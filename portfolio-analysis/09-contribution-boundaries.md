# 기여 경계 검증

## 1. 판정 원칙

이 문서는 커밋 작성자, PR·Issue 작성자, 실제 diff, 현재 파일 blame, 문서화된 요구사항을 함께 대조해 개인 기여와 공동 기여를 구분한다. 커밋 수는 탐색 단서일 뿐 기여율로 환산하지 않았다. GitHub에 사람 리뷰가 남아 있지 않은 경우에는 협업 방식 자체를 확인된 사실처럼 만들지 않았다.

- **A — 개인 기여로 직접 표현 가능**: 본인 커밋과 diff가 핵심 설계·구현을 직접 뒷받침한다.
- **B — 공동 기여로 표현 가능**: 본인이 중요한 일부를 구현했지만 현재 결과에는 팀원의 선행·후속 변경이 포함된다.
- **C — 프로젝트 수준 사실로만 표현**: 저장소에는 결과가 있으나 개인 소유권 또는 실제 운영 범위가 충분히 분리되지 않는다.
- **D — 본인 확인 전 사용 보류**: 로그·외부 환경·구두 협업 등 저장소 밖 증거가 필요하다.
- **E — 사용 금지**: 현재 증거와 모순되거나 다른 구성원의 기여를 개인 성과로 오인시킨다.

## 4. 역할별 기여 표기

| 활동 | 직접 확인된 본인 역할 | 표현 시 주의점 |
|---|---|---|
| 문제 정의 | 다수 Issue를 직접 작성하고 수용 기준과 작업 범위를 명시 | 실제 최초 발견자가 본인인지, 사용자 제보인지, 배포 로그인지 별도 확인 필요 |
| 설계 | 데이터 계약, DB 스키마, API 경계, 계산식, fallback을 문서·코드로 구현 | 팀원이 만든 상위 supervisor와 최종 UI를 포함해 “전체 설계”라 하지 않기 |
| 구현 | 위 다섯 영역의 핵심 파일 diff와 현재 blame 다수 소유 | 저장소 전체 기여율이나 커밋 비율로 확대하지 않기 |
| 리뷰 대응 | CodeRabbit의 구체 지적을 후속 커밋으로 해결한 사례 확인 | 사람 리뷰·페어 프로그래밍이 있었다고 추정하지 않기 |
| 검증 | 단위·통합 테스트 정의와 PR 본문의 실행 기록 일부 확인 | CI 배포가 테스트를 gate하지 않으므로 “모든 배포 전 자동 검증”이라 하지 않기 |
| 병합·배포 | 본인 PR이 merge되고 Actions 성공 기록 존재 | merge 승인 주체, 실제 사용자 트래픽, 배포 후 smoke test는 별도 증거 필요 |

## 5. 포트폴리오 표기 규칙
